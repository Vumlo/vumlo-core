# 0035. Submissions: drafts, attempts and deadlines

Status: Accepted
Supplements: ADR-0011, ADR-0021, ADR-0023, ADR-0025, ADR-0030

## Context
ADR-0011 fixed the shape of a submission (a draft, submitted attempts, per-assignment deadline settings) but not the rows, the arithmetic of the window, the order of the locks, or what the API returns. ADR-0021 left the second half of the delete guards (submitted work) to this task, ADR-0023 left `validate_submission` of the `AssignmentType` trait, and ADR-0025 left the third layer of editor limits (`config.editor.features` of an assignment). `assessment` owns an empty schema. This task builds the `text` type end to end. Auto-submit at the deadline needs the worker and is task 013b.

## Options
- **How a submit changes the data.** (a) Insert a new `submitted` row and delete the draft: two statements, and a window where both exist. (b) **Update the draft row to `submitted` in place**: one statement, atomic, and the row lock on the draft is the whole mutual exclusion.
- **Where the time comes from.** (a) `now()` in SQL: tests cannot move the clock. (b) **The handler reads the clock once and passes it down**; the service never reads it.
- **The assignment read that `assessment` and `gradebook` both need** (the row, its course, the release state of every row on its path, then course access and the `ViewContent` check). (a) A third copy of the SQL in `assessment`. (b) **One public read function in `content`** that both call, the way ADR-0030 allows `teaching::course_access`. (c) A neutral module for it: one more abstraction for two functions.
- **Discarding a draft after the window closed.** (a) Refused like a save. (b) **Allowed**: it is not a save, it removes unsubmittable work and changes nothing staff can see.

## Decision
1. `assessment.submissions` holds drafts and submitted attempts. There is at most one draft per (assignment, student). A submit turns the draft into attempt n+1; attempts are numbered from 1, per student and assignment. Submitted rows are never changed (a trigger refuses the update). Staff grade the latest submitted attempt and earlier attempts stay visible. Staff never see drafts.
2. A submit consumes the draft atomically, so a second submit without a new draft is `409`. This is the protection against a double click. There is no `Idempotency-Key` table in this task.
3. A draft may hold an empty document (autosave); a submit of an empty document is `422`. A document is empty when its `plain_text` is blank after trimming. A new draft after a submit starts empty; the client prefills it from the last attempt, which the API returns. Draft saves are last-write-wins and keep no versions. A student can discard their draft.
4. `content.assignments` gets the settings `due_at`, `on_deadline` (`keep_draft` | `auto_submit`), `accept_late`, `late_until` and `max_attempts` (`null` = unlimited), only for assignment types that take submissions (`text` now). If `due_at` is set, `on_deadline` and `accept_late` are required (no hidden defaults, ADR-0011): either all three of `due_at`, `on_deadline`, `accept_late` are set or none is. `late_until` needs `accept_late = true` and must be after `due_at`. `max_attempts` is at least 1. These rules are database `CHECK` constraints as well. A type that takes no submissions (`no_submission`) rejects these fields with `422`, and the database refuses them for that type. The `AssignmentType` trait gets `takes_submissions`, and `validate_submission` (ADR-0023).
5. The submission window closes at `due_at` when late work is not accepted, and at `late_until` (never, when null) when it is. After it closes, a submit and a draft save are `409`. A submit after `due_at` inside the window is stored with `is_late = true`. A student's own work before `due_at` is never late. The time is a parameter of the service call.
6. A change of the settings does not revalidate existing submissions and applies from the student's next action. Lowering `max_attempts` below a student's number of attempts only blocks further attempts.
7. `on_deadline = auto_submit` is stored and validated now and does nothing until task 013b (a known limit).
8. Only a current student of the course (`teaching.effective_members`, role `student`) who may view the published assignment can save or submit. Everyone else gets `404` where they may not see the assignment and `403` where they may see it but not do it (assistants, teachers and admins cannot submit). A student reads only their own submissions. An excluded student, and a student who left a linked group, are not on the roster and get `404`.
9. Staff (assistant, teacher, owner, admin) read: a list of an assignment's submissions (the latest submitted attempt of each current student, in roster order, with status and `is_late`; a student without a submission is listed with no attempt) and all attempts of one student. The attempts of a student are readable for a current student and for anyone who has a submitted attempt: an exclusion never touches submissions (ADR-0033).
10. A submit emits one `submission.submitted` event with ids only (ADR-0007). Saving or discarding a draft emits none.
11. The document of a draft is validated with the `student` profile as narrowed by the institution's configuration, and by the third layer of ADR-0025: `config.editor.features` of a `text` assignment narrows the profile further and can never widen it. An unknown feature, or one the effective `student` profile does not have, is `422` on `config`. The same check runs again when a draft is submitted, against the profile and the features as they are then.
12. Guards, the second half of ADR-0021: deleting an assignment, a module or a course (when course deletion exists) that has submitted attempts is `409`; drafts without any submitted attempt are purged with the deletion. Submit, draft save and discard take the assignment row `FOR SHARE` and read the settings from that locked row, as the grade write does (ADR-0030), so they serialize with a settings change and with a delete. A change of any assignment field takes the row `FOR UPDATE`.
13. The read that opens an assignment for a user and the read that locks it `FOR SHARE` are one public function each in `content` (`content::open_assignment`, `content::lock_assignment_shared`). `assessment` and `gradebook` call them, and `gradebook` loses its own copies. ADR-0030 point 8 reads: besides `teaching::course_access`, a module may call these two read-only functions of `content`.
14. Statement order. Draft save and submit: open the assignment (no lock, `404`), authorize (`403`), lock the assignment row `FOR SHARE` and read its settings and `config` from it, then check the window (`409`), then validate the document (`422`). Submit then locks the draft row `FOR UPDATE` (none: `409`), counts the attempts in a later statement (`max_attempts` reached: `409`), updates the draft row to `submitted` with the next number, and emits the event, all in the caller's transaction. Delete: lock the assignment rows `FOR UPDATE`, then ask the gradebook and `assessment` in later statements.

## Consequences
- Two submits of one draft end with exactly one attempt: the second waits for the draft row and then finds no draft. The unique index on `(assignment_id, student_id, attempt)` is the backstop.
- A submit that began before a settings change finishes under the old window; one that waits for the change sees the new one.
- The call graph gets a cycle between `content` and `assessment` (content guards its deletes with `assessment`, `assessment` opens assignments through `content`), like the one between `content` and `gradebook`. It compiles in one crate and is noted here instead of being hidden.
- `gradebook` reads an assignment through `content` now; its tests do not change.
- Known limits. `auto_submit` does nothing until task 013b. The student's `GET /items/{id}` still returns the whole `config`. There is no course deletion: when it exists it must lock the assignment rows `FOR UPDATE`, call `assessment::has_submitted_in_course` and then `purge_course`, as for the gradebook. Rights are checked before the row lock, as in the gradebook: a student removed in the same instant can still save one draft. The database `CHECK` for `no_submission` names a type, so a later type that takes no submissions needs a migration (the price of enforcing point 4 in the database; ADR-0008 has no check on `type`). The empty-document rule counts text only and must learn images and attachments when they exist.
- Not decided here: group work, "return for revision", submission status inside gradebook cells, the `Idempotency-Key` table, the worker.
