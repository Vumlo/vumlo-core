# 0025. Block documents (the canvas)

Status: Accepted
Supplements: ADR-0020, ADR-0021, ADR-0024

## Context
Rich text appears in many places: the `text` item, an assignment's description, the steps of a lesson, a question's prompt, its answer options and explanation, and a student's text answer. They should share one format, one editor and one validator. Teachers need Markdown-like writing with formulas, code, diagrams, images, video and files, and sometimes HTML for an animation. Version history and simultaneous editing are not needed.

## Options
Format: (a) HTML: sanitizing is hard and error-prone; (b) Markdown text: no block ids, weak for media, tables and per-block properties; (c) **a JSON block tree** of the shape editors such as BlockNote and TipTap use, as our own schema, so no editor library is built into the server.

Storage: (a) a separate documents table, which pays off only with versions or co-editing; (b) **inline `jsonb`** in the item, the lesson or the submission.

HTML blocks: (a) not supported; (b) rendered inside the page: a script would run with the reader's session; (c) **sandboxed and delivered separately**.

## Decision
- A document is a JSON object `{"v": 1, "blocks": [...], "attachments": [file_id, ...]}`, stored inline in `items.body`, in lesson steps, in question fields and in `submissions.content`. No versions, no co-editing.
- A block is `{"id", "type", "props", "content", "children"}`. Ids are strings, at most 64 characters, unique in the document and generated by the client. `content` is inline text: runs `{"text", "styles"}` with the styles bold, italic, strike and code, links `{"href", "content"}` and inline formulas. `children` nest list items.
- Block types: paragraph, heading (levels 1 to 3), bulleted, numbered and check list items, quote, divider, table, code (a `language` and plain text), math (a LaTeX block), mermaid, image, video and html. Sources of formulas, code, diagrams and HTML are plain text. The client renders them; the server never executes or renders them. A code block has a `language` from a fixed list in code (an unknown value is stored as plain text), and the client highlights it.
- Typing shortcuts (`**bold**`, `# `, fenced code) belong to the editor, not to the format.
- Features and profiles. The features are: headings, text_styles, links, lists, quote, divider, table, code, math, mermaid, image, video, attachments and html. A profile is the set of features a place allows. The profiles, defined in code, are:
  - `full`: every feature (`html` only under the rules below). Used by the `text` item, a lesson text step and an assignment description.
  - `question`: every feature except attachments and html. Used by a question's prompt and explanation.
  - `option`: text_styles, links, math, code and image. Used by an answer option.
  - `student`: headings, text_styles, links, lists, quote, divider, table, code, math, mermaid, image and attachments. Used by a student's text answer.
- Three layers of limits, each only narrowing the one before: the profile in code; the institution's config (`editor.profiles.<name>.features`); and, for the `student` profile, the assignment's `config.editor.features` (arrives with the submissions task). The server validates every document against the effective profile on each write and refuses a block outside it with 422 on the field. Clients read the effective profile from the API to build the toolbar.
- HTML blocks. The `html` feature exists only in `full` and only when the config switch `editor.html` is `true` (default `false`). Writing an html block is a `policy` action allowed to authors whose institution role is `teacher` or `admin`; an assistant who is an institution student cannot write one. The server does not sanitize HTML. It limits the size (256 KiB) and the author. Readers see it only in an `iframe` with `sandbox="allow-scripts"` and no `allow-same-origin`, so the page has an opaque origin and cannot reach the session or the API. The html is delivered by its own endpoint, which checks that the reader may see the item and answers with `Content-Security-Policy: sandbox allow-scripts; default-src 'none'; script-src 'unsafe-inline'; style-src 'unsafe-inline'; img-src data:`. It is never inlined into a page of the LMS origin and has no network access.
- Media. An image is an uploaded file only; external image urls are not allowed. A video is an uploaded file or a url on an allowlist of hosts (`editor.video_hosts`, default `www.youtube-nocookie.com` and `player.vimeo.com`). Links are http or https only. The server never fetches a url.
- Files. The files a document uses (in blocks and in `attachments`) are recorded in a reference table kept in step with each write, `content.item_files` for items and a matching table for submissions later. The `files` module serves a file only through an endpoint that authorizes through its owner: an item the reader may see (ADR-0010), or the submission rules. A file of a draft item is never served to a student, even if its id is guessed.
- Initial limits, raised by an ordinary change: a document is at most 1 MiB serialized and 6 levels deep; at most 20 attachments; a formula or a diagram at most 16 KiB; a code block at most 64 KiB.
- An unknown block type or property is refused on write. A change of the format bumps `v` and comes with an upgrade function.
- `plain_text(document)` extracts the text, for search, word counts and the AI agent.
- Validation lives in `content` as a public function. `assessment` calls it for student answers.

## Consequences
- The server needs one validator and a profile table; the frontend needs one editor configured by profile.
- HTML animations work without opening the session to scripts, at the cost of a second endpoint and a strict policy.
- The request body limit of the routes that accept documents must allow the sizes above.
- Markdown import and export can be added later without changing the format.
- Changing the `files` module's ADR must follow the file access rule above.
