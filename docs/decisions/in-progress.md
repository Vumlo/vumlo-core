- ADR-0070 — Module `ai_agent` ("Buddy"): a chat agent for students, teachers and admins, built on `module-api`; id `ai_agent`, never called "assistant" (a course role). One OpenAI-compatible adapter over `OutboundClient`, no new crate, no streaming. Its tools call existing service functions as the user's `Actor`, so it sees and does nothing the user cannot. Read tools run at once; every write is a stored proposal that runs only on the user's confirm (one request, one transaction, once). Students get a coach, never an author. One rolling chat per user in `mod_ai_agent`, deleted after `retention_days`, readable by nobody else. Admin settings: `endpoint`, `model`, secret `api_key`, `roles`, `daily_cap`, `retention_days`, `notice`. Built: the module with the chat, the read tools (`my_work`, `my_grades`, `teaching_overview`, `course_gradebook`), the cap, retention, the panel, and the proposal flow with the grading, deadline and content tools (`set_grade`, `publish_grades`, `set_deadline`, `create_module`, `create_text_item`, `create_assignment`, `create_quiz`; always drafts; `content::set_due_at` for the deadline). `ModuleState` carries `Institution` (the grading scale and the editor settings, nothing secret) so a module writes content under the core's own rules. A student's Buddy prepares `save_draft` and `submit_work` for text assignments, and the text of a draft must be words the student wrote in this chat (`tools::submitting::quoted`): text the model composed is refused, so the Buddy relays and never authors. An admin's Buddy also has `find_people` and `org_overview` and prepares `create_term`, `create_group`, `add_group_members` (students only, up to 50, all or none) and `reset_password`; `auth` and `org` export the service functions the admin routes already call. A reset is the one change with a secret: the confirm route makes and hashes the temporary password before its transaction, and the password is only in that response (`Cache-Control: no-store`), never in a proposal, the chat or a model prompt; the confirm answers `200 {temporary_password}` (null for every other change); an admin's own account is refused. All four packs of the plan are built. The desktop app shows the launcher: its `api` command carries the calls, it keeps no cached copy of `/modules/ai_agent/*` (offline, the Buddy is not drawn), and `POST …/messages` gets a 600 s timeout so a slow model is not taken for a lost connection.
- ADR-0071 — Modules get one launcher slot in `Shell`: a module with `web: true` may export a `Launcher` that the shell renders on every signed-in page (the Buddy button). No other slots; plugin tabs (0066) are unchanged. Built: `Shell` renders the `launchers` that `scripts/brand.mjs` collects from `web/src/modules/<id>/Launcher.tsx`.
- ADR-0083 — A clean install and an in-place update. `vumlo-cli brand apply` writes into the web app, not into a hidden folder: `web/src/generated/` (client config and types) and `web/public/brand/` (manifest, icons, `icon-1024.png` for the desktop installers); `.vumlo/`, `VUMLO_GENERATED_DIR` and `--generated` are gone, and an installation with no web app has nothing to brand (exit 0). `vumlo.toml`'s JSON Schema is printed by `config schema`. The accent colour is back (supersedes its removal in 0054): `institution.accent`, public, `violet` (default) | `blue` | `teal` | `green` | `orange` | `red`, one `--hue` in `tokens.css`, `data-accent` on the root element. The release archive ships `ai_agent` (only `dummy` is left out). **Security-relevant:** the base URL of a plugin may use `http://` for a host with a single label (`http://plugin-text-metrics:8000`, a container beside the core), through `check_plugin_endpoint`; a name without a dot cannot be a host on the public internet, an IP other than loopback and a dotted name still need `https://`, and no other caller of `check_endpoint` is relaxed. `./vumlo` and `update.sh --docker` also read `plugins/compose.yaml`. An installation is updated in place with `npx create-vumlo update` (it backs up what it replaces into `backups/` and never touches `vumlo.toml`, `.env`, `backups/` or `plugins/`). Built: everything in this repository. Missing: the release that carries it (0.5.0), and `create-vumlo` 0.3.0 with the pickers and the `update` command.
- ADR-0089 — The gradebook turns points into a result against a target. A course has `target` (default 100) and an optional `pass_mark`; its assignments sit in groups (`gradebook.groups`) that can have a cap, count only the best K, count as practice (graded, not in the total) or as bonus (in the total, not in what is reachable). The total is `min(target, sum of the groups)`; an empty mark is a zero. A course shows its groups in one of two layouts: `course` (a group stands for a top-level module; a row exists only once a rule is set) and `custom` (the teacher's own groups; an assignment with no mapping is in "Not sorted" and counts as a plain regular assignment). Switching layout deletes nothing. The "regular assignments total at most 100" rule of ADR-0022 is dropped (the target cuts the total instead); the twelve-point per-assignment limit stays, and on the `twelve` scale there is no course total. Replaces the out-of-scope list of ADR-0028 point 10 for categories; no weights in percent. Built: the migration `0048`, the pure computation (`gradebook/layout.rs`), the service and API (settings, groups, placement, structure, `my-grade-summary`, totals in the staff gradebook), and the web app: the Grade and Structure modes of the gradebook, the student's total. A template and a course made from one keep the settings, groups and placements (new keys for the teacher's own groups). Missing: the "Counts in" field of the assignment form.
- ADR-0090 — The gradebook is exported as a workbook: `GET /courses/{id}/gradebook/export.xlsx` (`ViewGradebook`; students by surname and name, one column per assignment, one subtotal per group, the total, the points earned before the target cut them, and the pass mark). Published values only, never a draft; a text cell is always written as a string, so a name that starts with `=` is not a formula. New crate `rust_xlsxwriter` 0.102 (MIT or Apache-2.0, no default features), added to ADR-0014; used only by `gradebook::export`. The headers are English until the server has a catalogue of its own.
- ADR-0095 — The admin console: administration moves out of the student app into a console on its own origin (`server.admin_origin`, required), with its own admin-only password login, its own cookie, short lifetimes, and a session `audience` (`app` or `console`) that administration actions require, so a problem in the student app cannot reach administration; the console and `create-vumlo` are the two things an administrator learns, `vumlo-cli` is the console's terminal twin. **Breaks, on purpose (accepted by the owner, one installation exists):** `/admin/*` stops answering an administrator's app session, and an installation without `admin_origin` does not start. An administrator keeps reading and editing any course, not enrolled, from the app (course oversight, audited). Built (plan 1): `GET /admin/courses` filtered (term, status, text) and paged, newest first, under the new action `ViewAllCourses`, and an "All courses" tab on `/courses` for an administrator, so the admin page keeps only the terms and the "Change owner" dialog is gone (course settings has the transfer); `plugins::set_setting_text`; `vumlo-cli plugin configure <id>` (one question per institution setting, answers read line by line, one transaction, one audit row per change), `vumlo-cli roles show|set` over `org::role_abilities` and `org::apply_role_abilities`, and a `doctor` line naming plugins that still need a setting (`plugins::missing_settings`). Built (plan 2): `auth.sessions.audience` (`app` or `console`; only a browser session can be console) carried into `Actor`; `access::authorize` gives the pure administration actions (people, institution, reports, terms, groups, unit abilities) and the admin branch of the unit actions to a console administrator only, while `ViewAllCourses` and every action inside a course keep `is_admin`, and `effective_unit_grant` gives an admin every ability on every unit only in the console; `POST /console/login` (admin-only, same answer for a non-admin as for a wrong password, its own throttle keys and rate limit), the `vumlo_console` cookie (`HttpOnly; SameSite=Strict; Secure`, no `Domain`), a console session of 30 minutes idle and 8 hours at most, refreshed after a minute; the credential channels (a bearer token and `vumlo_session` speak for the app, `vumlo_console` for the console, a token through the other channel is no credential, and with both cookies the request's `Origin` decides which is tried first, then the next is tried so a dead one never shadows a live one); `check_origin` per audience (`public_origin` or `allowed_origins` for the app, exactly `admin_origin` for the console), and `admin_origin` must differ from `public_origin` and `allowed_origins`; `vumlo-cli admin set-password`. Built (plan 3): `server.admin_origin` is public; `/admin/plugins/...` (list, status, grants, settings from the manifest spec with secrets write-only, call log) and `/admin/mail/...` (status, journal without addresses, retry) behind the new console-only actions `ViewPlugins`, `ManagePlugins`, `ViewMail` and `ManageMail`; the console itself is `web-admin/`, a Vite and React app of its own served as static files on `admin_origin` (it shares the framework-free parts of `web/src` through an alias and stands in for `next/link` and `next/navigation`), with people, groups, terms, institution, audit, units and roles, plugins and mail; the student app has no `/admin` pages and an "Admin console" link in an administrator's account menu; `deploy/Dockerfile.console`, a `console` service on 3001, the Caddy block of `VUMLO_ADMIN_DOMAIN`, a `web-admin` job in CI, and `vumlo-cli build web` builds it. Not in the console, on purpose: installing, removing and rotating the token of a plugin (they change the host and show a secret). Missing: the `create-vumlo` question for the admin address.
