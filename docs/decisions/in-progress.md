- ADR-0070 — Module `ai_agent` ("Buddy"): a chat agent for students, teachers and admins, built on `module-api`; id `ai_agent`, never called "assistant" (a course role). One OpenAI-compatible adapter over `OutboundClient`, no new crate, no streaming. Its tools call existing service functions as the user's `Actor`, so it sees and does nothing the user cannot. Read tools run at once; every write is a stored proposal that runs only on the user's confirm (one request, one transaction, once). Students get a coach, never an author. One rolling chat per user in `mod_ai_agent`, deleted after `retention_days`, readable by nobody else. Admin settings: `endpoint`, `model`, secret `api_key`, `roles`, `daily_cap`, `retention_days`, `notice`. Built: the module with the chat, the read tools (`my_work`, `my_grades`, `teaching_overview`, `course_gradebook`), the cap, retention, the panel, and the proposal flow with the grading, deadline and content tools (`set_grade`, `publish_grades`, `set_deadline`, `create_module`, `create_text_item`, `create_assignment`, `create_quiz`; always drafts; `content::set_due_at` for the deadline). `ModuleState` carries `Institution` (the grading scale and the editor settings, nothing secret) so a module writes content under the core's own rules. A student's Buddy prepares `save_draft` and `submit_work` for text assignments, and the text of a draft must be words the student wrote in this chat (`tools::submitting::quoted`): text the model composed is refused, so the Buddy relays and never authors. An admin's Buddy also has `find_people` and `org_overview` and prepares `create_term`, `create_group`, `add_group_members` (students only, up to 50, all or none) and `reset_password`; `auth` and `org` export the service functions the admin routes already call. A reset is the one change with a secret: the confirm route makes and hashes the temporary password before its transaction, and the password is only in that response (`Cache-Control: no-store`), never in a proposal, the chat or a model prompt; the confirm answers `200 {temporary_password}` (null for every other change); an admin's own account is refused. All four packs of the plan are built. The desktop app shows the launcher: its `api` command carries the calls, it keeps no cached copy of `/modules/ai_agent/*` (offline, the Buddy is not drawn), and `POST …/messages` gets a 600 s timeout so a slow model is not taken for a lost connection.

- ADR-0084 — The layer `mail`: all outgoing mail is a row, sent by one worker. A mandatory core crate `mail` with the schema `mail`, between `files` and `auth` (amends 0065: server → plugins → modules → learning → org → auth → mail → files → events → access → common; it takes over the delivery half of 0045). It depends on `common`, `events` and `vumlo-config` only; `lettre` and the `Mailer` move to it from `auth` (no new crate, ADR-0014 unchanged). It cannot read `auth`, so the caller above it passes each recipient (`Recipient {user_id, name, address}`) and the layer copies the address into the row. Nothing sends from a request or from an outbox handler. Tables (migration `0047_mail.sql`, no foreign key to another schema): `mail.batches` (one per enqueue: `plugin_id`, NULL for the core, `kind`, `subject`, `body`, `link_path`, counts), `mail.messages` (one per recipient: `user_id`, `to_address`, `to_name`, `plugin_id`, `kind`, `state` pending | sent | dead | cancelled, `attempts`, `run_after`, `expires_at`, `last_error`, `finished_at`, `erase_at`, `origin_id` unique), `mail.opt_outs (user_id, plugin_id, kind)`, `mail.dedupe (plugin_id, dedupe_key, user_id, at)` and `mail.signing_key` (one row of 32 random bytes made on first use). The worker is the outbox worker's twin (ADR-0045): every 2 s it claims 20 due rows with `FOR UPDATE SKIP LOCKED` and a 5-minute lease (`attempts` up, `run_after` moved), sends with no transaction open, and marks the row; a transient failure (no connection, SMTP 4xx) is retried after `events::backoff` (10 s doubling to 1 h); a permanent one (SMTP 5xx, an address the transport refuses) or an `expires_at` 24 hours after enqueue (a deadline reminder two days late is worse than none) makes it a dead letter; delivery is at-least-once; plugin mail checks the opt-out again right before sending and is then `cancelled`. `last_error` is a class (`smtp 451`, `connect`, `build`), never the server's text, which names the address. Retention: when a message is final, `erase_at` is `now() + mail.retention_days` for plugin mail and `now()` for account mail (its text holds a one-time link), and an hourly sweep sets `to_address`, `to_name` to NULL; a batch's `subject`, `body` and `link_path` go when its last address does; rows and batches are deleted after `mail.journal_days`; `mail.dedupe` after 30 days; nothing logged, audited or printed holds an address. `[mail]` gets `plugin_hourly_calls` 500 (1 to 100000), `recipient_daily` 20 (1 to 1000), `max_audience` 2000 (1 to 10000), `retention_days` 30 (1 to 3650) and `journal_days` 180 (`retention_days` to 3650) beside `from`, `link_base` and `transport.kind` = `smtp` | `file`; the section stays private and no key is secret except the SMTP password. **Account mail moves onto it with no change people see:** the `auth` handlers of `user.verification_requested` and `user.password_reset_requested` mint the token, compose the same en/uk text and call `mail::enqueue_account` in one transaction, with the outbox event id as `origin_id` (a rerun queues once, and a handler checks `mail::origin_queued` before it mints); the mail leaves at most a few seconds later, and a failure is a `dead` row for `vumlo-cli mail list` instead of a dead letter in the outbox. Account mail is never opt-out-able and never meets a plugin limit. Without `[mail]`: register and reset stay `404`, the plugin route is `503`, no worker starts, and messages already queued wait. The migration also adds `email_verified` to the view `auth.people` (a column at the end), which `learning` reads to mail only verified addresses. Rollback: there are no down migrations (0055); a release that carries this one is undone by restoring the backup taken before `db migrate`, since an older binary refuses a database that is ahead of it. Built: nothing yet. Missing: all of it (stages: config and crate, auth moved onto it, plugin route and scope, opt-out, CLI, docs and tests).
- ADR-0085 — Mail from plugins. New scope `mail:send` (the tenth; added to `Scope::ALL` and every list that enumerates scopes, so `plugin install` and `plugin upgrade` show it like any other). `POST /plugin-api/mail` with `{to: {user_id} | {course_id, audience: students | teachers | all}, kind, subject, text, link_path?, dedupe_key?}`: `kind` is a slug (`^[a-z][a-z0-9_-]{0,39}$`), `subject` 1 to 200 characters with no control character, `text` 1 to 20000 characters of plain text (line feed, carriage return and tab are the only controls), `link_path` at most 500 characters, one leading `/`, no `//`, no `\`, no whitespace or control character, made absolute with `mail.link_base` when the message is sent, `dedupe_key` at most 100 printable characters. Answer `202 {accepted, skipped, skipped_reasons: {opted_out, no_address, duplicate, disabled, rate_limited}}`, every reason present (the last is an addition to the plan, below). A plugin never sees an address. Order of answers: `401` token, `422` body, `403` scope, `503` mail not configured (problem: mail is not configured), then the target. **Recipients** are resolved by `learning::plugin_read::mail_recipients`, a flow above `auth` and `teaching`, as `contacts` and `members` already are: a `user_id` unknown to `auth.people` is `404`, one who is on the roster (`teaching.effective_members`) of no course the plugin reaches is `403`; a `course_id` is checked by `access::authorize_plugin_course` (unknown `404`, outside the grant `403`) and its audience read from `effective_members` (`students` = course role student; `teachers` = teacher and assistant, the staff who grade; `all` = both; an administrator who owns a course without a membership is on no roster and is not mailed). Only active users with a verified address (`auth.people.email_verified`) get mail; the others are counted `disabled` or `no_address`. An audience over `mail.max_audience` is `422` on `to` and queues nothing (not `429`, which would only make a plugin retry something that cannot succeed; an administrator raises the key for a larger course). **Limits:** per plugin, `mail.plugin_hourly_calls` accepted calls in the last hour (counted from `mail.batches` under a transaction advisory lock of the plugin, so the count is exact across processes): over it is `429` with `Retry-After` until the oldest call of the window leaves; per recipient, `mail.recipient_daily` plugin messages in 24 hours (account mail does not count): for a single `user_id` that is `429` with `Retry-After`, for an audience that person is skipped as `rate_limited` and the rest go; the daily limit per person, not the hourly one, is what bounds the total volume (people × 20 a day). **Dedupe:** `(plugin_id, dedupe_key, user_id)` is accepted once in 30 days, claimed atomically with `INSERT … ON CONFLICT DO UPDATE … WHERE at < now() - 30 days` in the same transaction as the message, so two concurrent calls queue one; a plugin that retries after a `5xx` should always send a `dedupe_key`. Order within one recipient: opt-out, then rate limit, then dedupe, so a skipped message claims nothing. **Audit:** one `events.audit_log` row per accepted call, source `plugin`, action `plugin.mail.send`, resource type `mail_batch` with the batch id, `meta` with the kind, the target ids (`user_id` or `course_id` and audience), the numbers accepted and skipped by reason, never a subject, text or address; a refused call (`403`, `404`, `422`, `429`) writes none. A plugin that is disabled or removed has its pending messages cancelled in the same transaction (`mail::cancel_pending`); enabling it again does not bring them back. **Content and trust:** the mail is plain text from the institution's `mail.from`, ends with a footer in the institution's language naming the plugin and the opt-out link (0086), and carries `X-Vumlo-Plugin: <plugin id>` and `Auto-Submitted: auto-generated`; the text may hold any URL a plugin writes, so `mail:send` is a grant to a plugin the administrator trusts to speak in the institution's name, which is why it is a scope an administrator approves, is limited, audited and signed in the footer. Built: nothing yet. Missing: all of it. Two points differ from the plan the tracks started from, for the reasons given: an oversized audience is `422` and not `429`, and `rate_limited` is a fifth skipped reason; `teachers` includes assistants.
- ADR-0086 — One-click opt-out. Every plugin mail ends with `…/api/v1/mail/opt-out/{token}` (under `mail.link_base`) and carries `List-Unsubscribe: <that link>` and `List-Unsubscribe-Post: List-Unsubscribe=One-Click` (RFC 8058), so a mail client offers its own button. The token is signed, not stored: `base64url("v1|user_id|plugin_id|kind") "." base64url(HMAC-SHA256(mail.signing_key, "vumlo-mail-optout|" payload))`, checked in constant time; it does not expire (an old mail must still work), and deleting the `mail.signing_key` row voids every link. `GET` and `POST /api/v1/mail/opt-out/{token}` need no session, no CSRF header and no body (the one-click POST sends a form the route ignores), upsert one row of `mail.opt_outs (user_id, plugin_id, kind)` and answer `200 text/plain` in the institution's language ("you will not get messages of this kind from <plugin>") with `Cache-Control: no-store`; the answer holds the matching `…/api/v1/mail/opt-in/{token}` link, which deletes the row the same way, because a mail scanner that fetches links will opt people out by `GET` and they must be able to undo it. A bad signature or a malformed token is `404` Problem Details and leaks nothing. The routes write only for a valid token and then only one row, so they carry no limiter of their own. An opt-out is per (user, plugin, kind) and covers plugin mail only; account mail has no opt-out. It is kept after the plugin is removed (a reinstall of the same id is still silenced) and is not audited (a person's own preference; ids only would add nothing). Built: nothing yet. Missing: all of it.
- ADR-0087 — The mail journal for the administrator. `vumlo-cli mail status` (counts of `pending`, `sent`, `dead` and `cancelled` in the last 24 hours and now, the age of the oldest pending message, the dead ones by plugin and kind, whether `[mail]` is set and which transport; exits 0), `mail list [--state S] [--plugin ID] [--kind K] [--user UUID] [--hours N] [--limit N] [--json]` (id, time, state, attempts, plugin, kind, user id, subject cut to 60 characters while it is kept, last error class; never an address) and `mail retry <message-id> | --dead [--plugin ID] [--dry-run]` (a dead message goes back to `pending` with `attempts` 0, `run_after` now and a fresh 24 hours; one whose address is already erased is reported and left; audited with the source `cli`, action `mail.retry`, `meta` with the count and the ids). They read and write `mail.*` through the public functions `mail::status`, `list` and `retry`. Built: nothing yet. Missing: all of it.
