## Foundations
- ADR-0001 — Modular monolith: one Rust binary and PostgreSQL, no Redis, broker or auth SaaS. Layout reshaped by 0065.
- ADR-0002 — One installation is one institution; no tenant id; institution settings live in the config file.
- ADR-0012 — One REST API under `/api/v1`, no client-specific endpoints, additive changes only.
- ADR-0013 — The frontend is a separate app on the public API, same site as the API behind a reverse proxy.
- ADR-0014 — The allowed core crates and their features. A new crate, version or feature needs an ADR.
- ADR-0016 — Module layout and transactions: routes → service → repo, the handler owns the transaction.
- ADR-0065 — Layered crates: server → plugins → modules → learning → org → auth → mail (0084) → files → events → access → common.
- ADR-0093 — `learning` is five crates in `backend/crates/learning/`: `teaching < content < assessment < gradebook < learning` (the last, in `flows/`, holds only the flows, the scheduler and the audit report), so a crate cannot name one above it (Cargo refuses most such edges as a cycle, `architecture.rs` checks the manifests for the rest). Across crates a reader sees only views the owner declared (migration 0054; grades: published values only), and what would go up is a flow in `learning` (`courses`, `items`, `submissions`, `files::check`) or a synchronous event subscriber: `events::emit` also runs the subscribers the composition root installed once (`events::install`, immutable, an emit with none installed is an error; an error aborts the change). `content.facts` (submitted, published score, marked) is the only thing the access rules read, rebuilt from the sources by `vumlo-cli facts rebuild`. A write that names files is a `begin_*` / `check` / `finish_*` triple in one transaction, the check locking the file rows in ascending id. Each crate has its own state, error enum and router. API and behaviour did not change. Spec: `docs/superpowers/specs/2026-11-12-split-learning-design.md`.
- ADR-0066 — Optional modules behind Cargo features, built on `module-api`; plugins installed and fed by events.
- ADR-0073 — New crate `chacha20poly1305` 0.11 (RustCrypto, feature `alloc`, no default features), added to ADR-0014. Used only by `plugins::secret::{seal, open}` for secret plugin settings: XChaCha20-Poly1305, a random 24-byte nonce per seal, key = HMAC-SHA256 of `plugins.secret_key` with a purpose label, associated data = install id and setting key. The sealed blob is `0x01 || nonce || ciphertext+tag` in base64url; the first byte is the format version. Replaces the hand-made HMAC construction of ADR-0072.
- ADR-0072 — Plugin settings. A manifest declares `settings` (a subset of JSON Schema: string, number, boolean, string with `enum`, list; `default`, `description`, `secret`, scope `institution` or `course`); an administrator sets them with `vumlo-cli plugin settings`; the core stores and validates the values per install, seals secrets with `plugins.secret_key` (XChaCha20-Poly1305, ADR-0073), shows no secret to anyone, and gives the values to the plugin at `GET /plugin-api/settings` (scope `settings:read`) and tells it by `plugin.settings.changed` (ids only, sent to that plugin alone). No web form yet.
- ADR-0074 — Plugin reads and course scoping. New scopes `assignments:read`, `roster:read`, `grades:read`, `quizzes:read`, `users:contact` beside `submissions:read`, `reports:write`, `settings:read`; read-only, `no-store`, and only what a student could be shown (submitted attempts, published grades, open assignments, a quiz without its key; an address only for people in a granted course). At install and with `plugin grant --courses`, an administrator gives a plugin `all` courses or a list (`plugins.install_courses`; existing installs are backfilled `all`); `access::authorize_plugin_course` decides: scope first, then course (unknown id `404`, outside the grant `403`), a list without `course_id` covers the granted courses, and the fan-out sends a plugin only the events of its courses. Lists use `?cursor=&limit=&updated_since=` with an opaque cursor over `(time, id)`; the roster has no change time and is a snapshot. The reads are `learning::plugin_read`. Amends ADR-0066 items 11 and 14.
- ADR-0075 — Events for plugins. A plugin subscribes explicitly (`subscribes` in the manifest) to `assignment.created` (an assignment first becomes visible), `assignment.updated`, `assignment.deadline_changed` (always with an update), `enrollment.changed`, `quiz.attempt_submitted` and `announcement.published`, beside `submission.submitted`, `grade.published` and `plugin.settings.changed`. Each is written in the transaction of the change with ids only; a draft emits nothing; delivery carries `occurred_at` (the outbox time, kept in `plugins.deliveries`); an event that names a course is sent only to a plugin that reaches it (ADR-0074). A change of group members is the internal `group.members_changed`, which a handler of `learning` turns into `enrollment.changed` per linked course and user. A user's status or role is covered by ADR-0082.
- ADR-0076 — Course announcements: `teaching.announcements`, plain text, created is published. Members read at `GET /courses/{id}/announcements`; staff and admins write (the rule of `EditContent`), edit at `PATCH /announcements/{id}` and delete; only publishing is an event. New scope `announcements:read` and `GET /plugin-api/announcements`. No web screen yet.
- ADR-0077 — Plugin reports at three levels. `reports:write` covers a report on a submitted attempt, an assignment or a course, `PUT|DELETE /plugin-api/{submissions|assignments|courses}/{id}/reports/{key}`; the key (a slug of at most 40 characters) makes it replaceable, a plugin keeps at most 20 per subject, and the course grant of ADR-0074 applies. One table, `plugins.reports`, with exactly one of three cascading keys (and a generated `subject_id` in its primary key). Staff who may see the subject read them at `GET /{submissions|assignments|courses}/{id}/plugin-reports`. Replaces `PUT /plugin-api/submissions/{id}/report` (amends ADR-0066 item 15).
- ADR-0078 — Routes of a plugin's own server, through the core. The manifest may declare `routes` (≤ 20): method (GET, POST, PUT, PATCH, DELETE), a path of plain segments or `{name}` (`{course_id}` is a course), `roles` (institution roles; an administrator only if `admin` is listed) and optional `course_roles` (teacher, assistant, student in the course of `{course_id}`; an allowed administrator is not asked for one). `ANY /api/v1/plugins/{id}/{path}` takes the person with the session the core already checks (cookie with its CSRF rule, or bearer), finds the declared route (no route: `404`), resolves the course (not visible: `404`; not in the plugin's grant: `403`), lets `access::authorize_plugin_route` decide (`403`), and forwards the call to `{base_url}{path}?{query}` with `Content-Type`, `Accept` and `Accept-Language` only and the signed `X-Vumlo-User`, `-Role`, `-Course`, `-Course-Role`, `-Timestamp`, `-Nonce` and `-Signature`: `HMAC-SHA256(secret, timestamp "." canonical)` over `vumlo-proxy`, nonce, method, request-target, user, role, course, course role and the SHA-256 of the body. No cookie or authorization header reaches the plugin; a header of the caller named `X-Vumlo-*` is dropped. Replay: a fresh UUID nonce and the time on every call; the plugin refuses a call more than 300 s off or a nonce it has seen (the example does both). Segments that could climb or escape (`.`, `..`, `%`) match nothing. The answer is the plugin's, but is served from the core's origin, so only JSON, `application/problem+json`, text, CSV, iCalendar, PDF and XLSX are passed on (`nosniff`, `Content-Security-Policy: sandbox; default-src 'none'`, `no-store`; the plugin's own cookies, CSP and caching are dropped, a `Content-Disposition` only if it is `attachment`); another type, a redirect or a `5xx` is `502`, an unreachable plugin `502`, one that takes over 30 s `504`. 2xx and 4xx are passed on with their body. Bounds: 10 MiB in, 20 MiB out, no redirects.
- ADR-0079 — Running plugins that are in use. `vumlo-cli plugin upgrade <id> [--grant ...] [--dry-run]` reads the manifest again from the stored address (the id must be the same), prints what changed (version, scopes, events, settings, routes, pages) and asks only about scopes the plugin did not ask for before; everything else follows the manifest, a grant for a scope it no longer asks for goes, stored setting values that no longer fit (setting gone, other scope, secret turned plain or the reverse, no longer meeting the spec) are removed and reported, the plugin is sent `plugin.settings.changed`, and the token, the secret, the courses and the grants it keeps are untouched; audited (`cli`). `plugin rotate-token <id>` replaces the token in one statement (the old one is `401` at once) and prints the new one once; audited. Every call to `/plugin-api` counts against an allowance of its own install (`plugins.api_burst`, `plugins.api_requests_per_second`; calls with no good token share one allowance, so garbage cannot grow the limiter or use up a real plugin's) and a call over it is `429` with `Retry-After`; it is not logged. Each other call leaves a line in `plugins.api_calls` (plugin, method, route template, answer, milliseconds: no id, query or content), kept `plugins.call_log_days` (30) days by the delivery worker and read with `vumlo-cli plugin calls <id> [--hours] [--limit]`. A plugin's writes (reports) are audited in `events.audit_log` with the source `plugin`, no actor and `meta` naming the plugin, in the transaction of the write; reads are not.
- ADR-0080 — Public routes of a plugin. A route in the manifest may say `auth = "none"` (the default is `session`, ADR-0078); then it is `GET` only, has no `roles`, `course_roles` or `{course_id}` (the manifest is refused otherwise), and `ANY /api/v1/plugins/{id}/{path}` serves it with no session, for a calendar feed that an app fetches with a URL alone. The proxy finds the install and the route first; a route that is not public (or is not there) still asks for the session first, so a stranger gets `401` as before. For a public route the core takes one call from a token bucket kept for that route (`plugins.public_route_burst` 10, `plugins.public_route_requests_per_second` 2: one allowance for everyone who calls it, since nobody is identified and an address behind a proxy is not trusted to tell callers apart; over it is `429` with `Retry-After`, and the plugin is not called). It forwards with the same allow-list of headers (no cookie, no `Authorization`, nothing named `X-Vumlo-*`), without `X-Vumlo-User`, `-Role`, `-Course`, `-Course-Role`, with `X-Vumlo-Anonymous: 1`, and the signature of ADR-0078 gets a line `session` or `none` after the target, and `-` for the user and the role of a call that is `none`, so an anonymous call and a person's call never verify as each other (`X-Vumlo-Anonymous` is a hint; what is signed decides). The answer is restricted as for any route. The plugin must check its own token: the core says only that nobody is signed in. A public route is stored in `plugins.plugin_installs.routes` as `auth: "none"` (no migration; a route stored before has none and is `session`); `plugin upgrade` shows a route that changed `auth` as removed and added (`GET /feed/{name} (public)`). Amends ADR-0078.
- ADR-0081 — What was deleted, for plugins that sync by `updated_since`. `teaching.tombstones (kind, id, course_id, deleted_at)` is written by database triggers in the transaction of the delete, whatever deletes the row (an item, its module, the course): one for each **published** assignment (`content.items` of kind `assignment`; a draft was never shown) and one for each announcement. A plugin reads `GET /plugin-api/assignments/deleted` (scope `assignments:read`) and `GET /plugin-api/announcements/deleted` (`announcements:read`) with a required `deleted_since` (inclusive RFC 3339), `course_id`, `cursor`, `limit`, and gets `{items: [{id, course_id, deleted_at}], next_cursor}` ordered by `(deleted_at, id)`; the course grant of ADR-0074 applies (a course outside it is `403`; a course that is itself gone is not a `404`, since its deletions are the point). **Retention:** `plugins.tombstone_days` (30, 1 to 3650); the delivery worker deletes older rows about once an hour (with the call log), and a `deleted_since` older than the retention is `410`, which tells the plugin to read the list in full. `deleted_at` is the start time of the transaction, so a plugin catches up from a time a little before the last one it saw and takes an id twice without harm. **Not covered, on purpose:** submitted attempts and grades are never deleted (the guards of ADR-0028 and ADR-0035 refuse to delete an assignment or a course that holds either, and a published grade only changes), so they have no list; the roster (`GET /courses/{id}/members`) is a full snapshot, so a member who left is absent from it and the event `enrollment.changed` says when to read it; an assignment that stops being visible to students is not deleted, it stops being listed and its id is `404`.
- ADR-0088 — The "Plugin reports" panel in the web app (display convention v1). Staff see what plugins stored under ADR-0077 on the grading view of a submitted attempt, on the assignment page and on the course page of the staff; a student's screens never mount it and never ask. A report is always shown by its `summary`; `data.display` (`level` ok|info|warn|alert, `title` of at most 80 characters, `table` of at most 200 rows of strings or numbers, `facts` of at most 20, `links`) adds a badge, a heading, a table, a list of figures and buttons. Everything is text (no HTML, no markdown); a link is rendered only if its `path` starts with `/api/v1/plugins/<the same plugin id>/` (no `.`/`..`, no host) and is a plain anchor the browser follows with the session cookie; numbers follow the viewer's language; a missing or invalid `display` falls back to `summary` and the raw JSON folded away. The desktop app shows no links. `web/src/components/PluginReports.tsx`, `web/src/lib/pluginReport.ts`.
- ADR-0082 — `enrollment.changed` also follows a user's role and status. When `learning::people::update_user` changes a user's institution role or status (a new name changes nothing), it writes `enrollment.changed {course_id, user_id}` in the same transaction for every course whose roster the user is on or could be on (a membership, or a linked group with no exclusion; `teaching.courses_with_user`) and for each course a demotion took a teacher membership from (`drop_teacher_memberships` now returns those courses and no longer emits itself, so a course is announced once). Why: a disabled student leaves every roster, and a group brings only students, so a role change moves a person between rosters, with no membership row changing. A change of a course membership's role was already announced (ADR-0075). Amends ADR-0075.
- ADR-0084 — The layer `mail`: all outgoing mail is a row, sent by one worker. A mandatory core crate `mail` (schema `mail`, migration `0047_mail.sql`) between `files` and `auth` (amends 0065: server → plugins → modules → learning → org → auth → mail → files → events → access → common; it takes over the delivery half of 0045). It depends on `common`, `events` and `vumlo-config`; `lettre` and the `Mailer` moved to it from `auth` (no new crate). It cannot read `auth`: the caller above passes each recipient (`Recipient {user_id, name, address}`) and the layer copies the address into `mail.messages` (one row per recipient; `mail.batches` holds one row per enqueue). Also `mail.opt_outs`, `mail.dedupe` and `mail.signing_key`; no foreign key to another schema. The worker (`mail::run_worker`, in `serve` and `worker`) is the outbox worker's twin: every 2 s it claims 20 due rows with `FOR UPDATE SKIP LOCKED` and a 5-minute lease, sends with no transaction open, retries a transient failure after `events::backoff`, and makes a permanent failure or a message 24 hours old a `dead` row; delivery is at-least-once. `last_error` is a class (`smtp 451`, `connect`), never the server's text. A final message is erased (`to_address`, `to_name` NULL) at once for account mail and `mail.retention_days` later for plugin mail; a batch's subject, body and link go with its last address; rows are deleted after `mail.journal_days`; no log, audit row or CLI line holds an address. `[mail]` gained `plugin_hourly_calls` 500, `recipient_daily` 20, `max_audience` 2000, `retention_days` 30 and `journal_days` 180 (all private, validated at load). Account mail (verification, reset) goes through it: the `auth` handlers mint the token, compose the same en/uk text and call `mail::enqueue_account` in one transaction with the outbox event id as `origin_id`; it is never opt-out-able and never meets a plugin limit. Without `[mail]`: register and reset stay `404`, the plugin route is `503`, no worker starts. The migration also adds `email_verified` to the view `auth.people` (last column). Rollback: there are no down migrations (0055); restore the backup taken before `db migrate`, since an older binary refuses a database that is ahead of it. Built: all of it.
- ADR-0085 — Mail from plugins. Scope `mail:send` (the tenth). `POST /plugin-api/mail` with `{to: {user_id} | {course_id, audience: students | teachers | all}, kind, subject, text, link_path?, dedupe_key?}` answers `202 {accepted, skipped, skipped_reasons: {opted_out, no_address, duplicate, disabled, rate_limited}}`, every reason present; a plugin never sees an address. Answers in this order: `401`, `422` (body), `403` (scope), `503` (no `[mail]`), `404`/`403` (target), `429`. Recipients come from `learning::plugin_read::mail_recipients`: a `user_id` must be on the roster of a course the plugin reaches, a `course_id` must be one it reaches; `teachers` is teacher and assistant (an administrator who owns a course without a membership is on no roster); only active users with a verified address are mailed, the rest are counted (a disabled student is not on a roster at all, ADR-0037). An audience over `mail.max_audience` is `422` on `to` and queues nothing (a retry could never succeed, so not `429`). Limits: `mail.plugin_hourly_calls` accepted calls per plugin per hour (exact: counted under a per-plugin advisory lock in the caller's transaction), `429` with `Retry-After`; `mail.recipient_daily` plugin messages per person in 24 hours: `429` with `Retry-After` for one `user_id`, a `rate_limited` skip inside an audience. `(plugin, dedupe_key, person)` is accepted once in 30 days, claimed in the transaction of the message; per recipient the order is opt-out, daily limit, dedupe, so a skipped message claims nothing. One `events.audit_log` row per accepted call (source `plugin`, `plugin.mail.send`, resource `mail_batch`, ids and counts by reason, never text or address). Disabling or removing a plugin cancels its pending mail in the same transaction (`mail::cancel_pending`); enabling it again does not bring it back. The mail is plain text from `mail.from` with a footer that names the plugin and the opt-out link, `X-Vumlo-Plugin` and `Auto-Submitted`; the text may hold any URL, so `mail:send` is for plugins the administrator trusts to speak in the institution's name. Differences from the plan the tracks started from: the oversized audience is `422`, `rate_limited` is a fifth reason, the hourly limit counts calls, not messages. Built: all of it.
- ADR-0086 — One-click opt-out. Every plugin mail carries `List-Unsubscribe` with `…/api/v1/mail/opt-out/{token}` (under `mail.link_base`) and `List-Unsubscribe-Post: List-Unsubscribe=One-Click` (RFC 8058), and ends with the same link. The token is signed, not stored: `base64url("v1|user_id|plugin_id|kind") "." base64url(HMAC-SHA256(mail.signing_key, "vumlo-mail-optout|" payload))`, checked in constant time, never expiring; deleting the `mail.signing_key` row voids every link. `GET` and `POST /api/v1/mail/opt-out/{token}` need no session, no CSRF header and ignore any body (the one-click form); they upsert one row of `mail.opt_outs (user_id, plugin_id, kind)` and answer `200 text/plain` in the institution's language with `Cache-Control: no-store` and the matching `…/mail/opt-in/{token}` link, which deletes the row (a mail scanner that opens links will opt people out by `GET`). A bad or malformed token is a `404` Problem Details. An opt-out is per (user, plugin, kind), covers plugin mail only, is kept after the plugin is removed, and is checked again right before sending (a queued message becomes `cancelled`). It is not audited. Built: all of it.
- ADR-0087 — The mail journal for the administrator. `vumlo-cli mail status [--json]` (pending, sent, dead and cancelled counts, the oldest pending message, the dead ones by plugin and kind, which transport `[mail]` names), `mail list [--state S] [--plugin ID] [--kind K] [--user UUID] [--hours N] [--limit N] [--json]` (id, time, state, attempts, plugin, kind, user id, subject cut to 60 characters, error class; never an address) and `mail retry <message-id> | --dead [--plugin ID] [--dry-run]` (a dead message goes back to `pending`; one whose address is already erased is reported and left; audited with source `cli`, action `mail.retry`, `meta` with the count and the ids, no row when nothing was put back). They use the public functions `mail::status`, `list` and `retry`. Built: all of it.
- ADR-0054 — Deployment: `vumlo-cli`, one config schema, build-time branding, optional modules.
- ADR-0036 — Each test gets its own database and pool (`db_test`); the harness is the `test-support` crate.

- ADR-0092 — Completion and access rules. A module or an item carries an optional **rule**: a list of conditions that must all hold (`access_rule: {all: [...]}` on `PATCH /modules/{id}` and `PATCH /items/{id}`; `null` removes it, absent keeps it). A condition is `completed` (an item, or a module: every item in it and in its sub-modules) or `score_at_least` (an assignment's published score). A rule on a module also locks what is in it. **Locked is visible, not hidden:** the title stays in the tree and the student's reads carry `standing: {done, locked: [unmet conditions with the title of what each names, when the student can see it]}`; a locked item reads as its title only (empty `body`, no assignment `config`), its files are `404`, saving a draft, submitting and uploading are `409`, search does not match or quote its text, `item-meta` gives no reading time, and a plugin tab is not offered. Staff are never locked; they read the rule as `access_rule`, a student never does. **Done** is derived: an assignment is done when the student has a submitted attempt or a published score; a text or file item when the student marks it (`PUT`/`DELETE /items/{id}/completion`, action `MarkDone`, `409` for an assignment, a locked item or an archived course). The rule is rows (`content.access_conditions`, foreign keys with `ON DELETE CASCADE`), so deleting what a condition names removes the condition instead of locking the node for good; a copy of a course or a template copies the rules and points them at the copies. A rule is refused (`422` on `access_rule.all[i].<field>`) when it names something outside the course, itself, a score on a non-assignment, points above what the assignment is worth, more than 10 conditions, or when the rules would make a circle (an item that waits for its own module, two nodes that wait for each other); writers of one course's rules take turns. The logic is pure in `content::rules` (done, unmet, cycle) and `content::standing` puts it on the tree. Migration `0050`. Not built: "any of" and date conditions (`publish_at` covers dates), a staff progress matrix, events for completion.
- ADR-0097 — Activity types: the kind of an assignment is a contract and a registry instead of a closed enum and type names in SQL and services; ADR-0008's `AssignmentType` is now the plugin boundary. The crate `learning/activity` (no schema, beside the chain; its manifest lists only plain data crates and `architecture.rs` checks it) holds the trait `ActivityType` (`id`, `capabilities`, `completion`, eight of the nine methods of the old `AssignmentType` (`takes_submissions` became `capabilities().submissions`), and the file hooks `config_file_refs`, `submission_file_refs`, `check_file_names`), `Capabilities { submissions, auto_graded }`, `CompletionPolicy` (`SubmittedOrGraded` or `Graded`), the shared data its signatures name, and the rich-text document model moved from `content`. The registry is filled once by the composition root next to `events::install` (`server` and `vumlo-cli` call `activity::install` with `content::builtin_types()`; `install`, `get`, `available`, `ids_where`); `get` before `install` is an error, and `Kind` decodes as text through the registry, so an unknown stored type is a decode error. The five built-ins (`text`, `no_submission`, `file`, `form`, `quiz`) implement the trait in `content`; `BuiltinType` and `AssignmentType` are gone. Code asks a capability, never a name: the gradebook's SQL binds `ids_where(..)` as `text[]` instead of `'no_submission'` and `'quiz'`; the quiz result, form responses and the text an agent writes stay the types' own features, tied to `quiz::ID`, `form::ID` and `text::ID`. Completion is decided by the type's policy in `content::repo::facts` with the same answer as before (`no_submission` is `Graded`, the other four are `SubmittedOrGraded`); the teacher chooses nothing. `content.assignments.type` stays free text, and the CHECKs of migrations 0017 and 0026 stay (the migration that adds the first other submission-less type drops them). Later: the per-activity completion choice and the events `activity.completed` and `course.completed` (roadmap item 4), a type that comes from a module (the edge `module-api -> activity`), and the capabilities in the web app (its per-type pages and `no_submission` filters stay). Spec: `docs/superpowers/specs/2026-11-14-activity-types-design.md`.

(1) `assignment.created` is sent when students can first see a published assignment (the course, the module path and the item are published and no `publish_at` lies ahead), not when it is published: `content.items.announced_at` is set by `content::announce_visible`, which the publish routes of an item, a module (also without `cascade`) and a course call for their course, and the scheduler calls for all of them; this also fixes the silent gaps (a course publish, a module publish without cascade) and replaces the `item.published` event of ADR-0010, which nothing consumed.
