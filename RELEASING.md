# Releasing

Release only from `main`, with CI green on the commit you tag and `CHANGELOG.md` written. Before 1.0 a
**minor** version (`0.2.0`) is for anything that changes the configuration (`config_version`), the API
or the migrations; a **patch** version (`0.1.1`) is for fixes that need none of those. Whoever installs
a release reads its **Upgrade notes** in the changelog first.

What is published is a **source archive**, `vumlo-X.Y.Z-source.tar.gz`, with `SHA256SUMS`, attached to
the GitHub Release. Administrators install from it ([docs/install.md](docs/install.md)); they never
clone this repository.

1. Branch from `main`. Set the new version in all three places (a test fails if they differ):
   `[workspace.package] version` in `backend/Cargo.toml`, `"version"` in `web/package.json`, and the
   default of `VUMLO_VERSION` (twice) in `deploy/compose.yaml`. Run `cargo update --workspace` in
   `backend/` so `Cargo.lock` follows.
2. In `CHANGELOG.md` move the `[Unreleased]` entries under `## [X.Y.Z] - YYYY-MM-DD`, write the
   **Upgrade notes** (a new `config_version`, a manual step, the migrations that run), and update the
   links at the bottom. If the archive's contents change (a new directory an administrator needs),
   change the allowlist in `.github/release/make-archive.sh`.
3. Run the checks of `AGENTS.md` §14, and `.github/release/make-archive.sh X.Y.Z /tmp/dist` followed by
   `.github/release/verify-archive.sh /tmp/dist X.Y.Z` (it needs Docker and takes a while). Merge the
   branch once CI is green.
4. Tag the merge commit on `main` and push the tag: `git tag -a vX.Y.Z -m vX.Y.Z && git push origin vX.Y.Z`.
5. The `Release` workflow checks that the tag is the workspace version and on `main`, runs the CI
   checks again, builds the archive from the allowlist, builds and runs it from scratch in a clean
   directory (the Docker path of `docs/install.md`), and only then creates the GitHub Release with the
   changelog entry as its notes. Check that the Release has the archive and `SHA256SUMS`.

A published tag is never moved or deleted. If a release is wrong, fix it on `main` and release the
next patch version.

## What the archive contains

An explicit allowlist: `backend/` (the crates, the migrations, the offline SQL data, the lockfile),
`web/`, `deploy/`, `brand/` (the placeholder logo), the `vumlo` script, `docs/install.md`,
`CHANGELOG.md`, `README.md`, and `vumlo.toml.example`. Not in it: the tests directories, the ADRs,
`ARCHITECTURE.md`, `AGENTS.md`, the CI files and the development compose file.

The test-only module `dummy` is removed, and that changes manifests: the archive carries release
manifests, generated by `make-archive.sh` from the tagged files: it deletes the module from the
workspace members and the workspace dependencies, the `dummy` feature and optional dependency of
`server` and `vumlo-cli`, the module's two lines in `server/src/modules.rs` and
`vumlo-cli/src/runtime.rs`, and its offline query data, then lets cargo drop it from `Cargo.lock`
(and fails if anything else in the lock changed). The unit tests that live inside `src/` files cannot be
separated from the code and ship with it.

## Experimental

Nothing experimental is in a release. The only module in the repository, `dummy`, exists to test the
module mechanism (ADR-0054) and is never in the archive. A real optional module (`ai-agent`, `vpl`, ...)
that is not finished stays out of the allowlist and out of the release manifests the same way, and is
listed here, with the reason, until it is ready.
