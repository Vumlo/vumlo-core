# Releasing

Release only from `main`, with CI green on the commit you tag and `CHANGELOG.md` written. Before 1.0 a
**minor** version (`0.2.0`) is for anything that changes the configuration (`config_version`), the API
or the migrations; a **patch** version (`0.1.1`) is for fixes that need none of those. Whoever installs
a release reads its **Upgrade notes** in the changelog first.

What is published is a **source archive**, `vumlo-X.Y.Z-source.tar.gz`, with `SHA256SUMS`, attached to
the GitHub Release. Administrators install from it ([docs/install.md](docs/install.md)); they never
clone this repository.

1. Branch from `main`. Run `node .github/release/set-version.mjs X.Y.Z`. It sets the version in every place (a test fails
   if they differ): `[workspace.package] version` in `backend/Cargo.toml` (the one the rest follows), `"version"` in
   `web/package.json` and `desktop/package.json` and their lockfiles, `version` in the `[package]` of `desktop/Cargo.toml`, the
   default of `VUMLO_VERSION` (twice) in `deploy/compose.yaml`, and both `Cargo.lock` files. It also opens the changelog entry
   (step 2). A new place that carries the version is added to that script.
2. In `CHANGELOG.md` move the `[Unreleased]` entries under the `## [X.Y.Z] - YYYY-MM-DD` heading the script made (its compare
   links are made too), and write the **Upgrade notes** (a new `config_version`, a manual step, the migrations that run). If the
   archive's contents change (a new directory an administrator needs), change the allowlist in `.github/release/make-archive.sh`.

   What follows a release by itself: the docs and the version shown on the landing site (fetched from the newest release when it
   is built), the demo (`Follow the core release` there opens a pull request that moves its `VERSION`) and `npx create-vumlo`
   (it downloads the newest release). Only the deploys of the landing site and the demo, and `npm publish` of a new
   `create-vumlo`, are by hand.
3. Run the checks of `CLAUDE.md` §14, and `.github/release/make-archive.sh X.Y.Z /tmp/dist` followed by
   `.github/release/verify-archive.sh /tmp/dist X.Y.Z` (it needs Docker and takes a while). Merge the
   branch once CI is green.
4. Merge the branch. **That is the release:** the `Release` workflow runs on every push to `main`, finds a
   workspace version whose tag `vX.Y.Z` does not exist yet, and releases it. A pull request is checked once, by
   CI; the release runs the CI checks again on the merged commit (they include the test that the versions agree).
5. The `Release` workflow builds the archive from the allowlist, builds and runs it from scratch in a clean
   directory (the Docker path of `docs/install.md`), and only then creates the GitHub Release, and with it the tag
   `vX.Y.Z` on the commit it checked, with the changelog entry as its notes (an empty entry fails it). If any step
   fails, no tag and no Release exist: fix it on `main` and the next push tries again. A push to `main` whose
   version is already tagged does nothing. Check that the Release has the archive and `SHA256SUMS`.

A published tag is never moved or deleted. If a release is wrong, fix it on `main` and release the
next patch version.

## What the archive contains

An explicit allowlist: `backend/` (the crates, the migrations, the offline SQL data, the lockfile),
`web/`, `desktop/` (the desktop app, ADR-0056; its tests are left out), `deploy/`, `brand/` (the Vumlo logo and mark), the `vumlo` script, `docs/install.md`, `docs/desktop.md`,
`docs/img/` (the screenshots of `README.md`), `CHANGELOG.md`, `README.md`, and `vumlo.toml.example`. Not in it: the tests directories, the ADRs,
`ARCHITECTURE.md`, `docs/PLAN.md`, `CLAUDE.md`, `AGENTS.md`, the CI files and the development compose file.

The real optional modules (`ai_agent`) ship, so that `npx create-vumlo` can offer them. The test-only module `dummy` is
removed, and that changes manifests: the archive carries release
manifests, generated by `make-archive.sh` from the tagged files: it deletes the module from
the workspace dependencies, the `dummy` feature and optional dependency of
`server` and `vumlo-cli`, the module's two lines in `server/src/modules.rs` and
`vumlo-cli/src/runtime.rs`, and its offline query data, then lets cargo drop it from `Cargo.lock`
(and fails if anything else in the lock changed).

Unit tests never live inside a source file: `foo.rs` has `#[cfg(test)] mod tests;` and the tests are in
`foo/tests.rs` (`mod.rs`, `lib.rs`: `tests.rs` beside it). The script deletes every `tests.rs`, and fails
if one is left; the declaration stays, and does nothing outside a test build. A new test module follows
that naming, or it ships. The test database harness is the crate `backend/crates/test-support`, a
dev-dependency of every crate that tests against a database: the script deletes it with its lines in the manifests (those
of the crates in `backend/crates/learning/` too), and `verify-archive.sh` checks that neither it nor any
`tests.rs` is in the archive. An integration-test folder `tests/` of a crate in `crates/`, `crates/learning/` or
`crates/modules/` is deleted as a whole.

## Experimental

Nothing experimental is in a release. The only module in the repository, `dummy`, exists to test the
module mechanism (ADR-0054) and is never in the archive. A real optional module (`ai-agent`, `vpl`, ...)
that is not finished stays out of the allowlist and out of the release manifests the same way, and is
listed here, with the reason, until it is ready.
